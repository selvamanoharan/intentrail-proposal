IntentRail: authorization-bound execution for A2A

Status: Discussion draft  ·  Last updated: 3 August 2026  ·  Proposed artifact: experimental-ext-intentrail

IntentRail is a proposed A2A lifecycle extension for actions that have external side effects. The narrow goal is to bind what the requester intended, what was authorized, what was executed, and what outcome was observed.

This is a proposal for community discussion. It is not a request to change the A2A core transport or introduce a new identity, policy, or reputation system.

The problem

A task can be authenticated and authorized, but that does not by itself prove that the same action was executed later.

Between authorization and execution, several things can go wrong:

  • parameters can change;
  • constraints can expire or be revoked;
  • an authorization can be reused;
  • a different recipient or resource can be substituted; or
  • a completion message can claim an outcome that is not linked to the authorized action.

A2A provides the task and message lifecycle. IntentRail would define the additional invariants needed at the execution boundary.

Proposed flow

StageQuestionMinimum record
Preflight What exact action, parameters, constraints, and expected outcome are requested? A deterministic digest of the request and constraints
Authorization May this exact request execute for this task and attempt? A decision bound to the task, attempt, digest, scope, and validity window
Execution Does the concrete action still match immediately before the side effect? A one-use execution record linked to the authorization
Outcome What was observed, and does it correspond to the authorized action? An outcome record or evidence reference linked to the execution
Compatibility constraint The extension should use existing A2A task states and namespaced extension metadata. It should not add new values to A2A core enums.

Example

Requested action
  transfer 100 USD to vendor-A

Authorization
  allow once
  amount must equal 100 USD
  recipient must equal vendor-A
  valid for task T, attempt 1

Attempt: transfer 500 USD to vendor-A
  rejected before the side effect because the amount changed

Attempt: transfer 100 USD to vendor-A
  permitted; authorization is consumed

Replay: transfer 100 USD to vendor-A
  rejected because the authorization has already been used

Outcome
  references the execution record and the authorization that permitted it

Scope

What IntentRail would define

  • A versioned A2A extension identifier and activation rules.
  • A minimal preflight record for action, parameters, constraints, and expected outcome.
  • A binding between an authorization decision, task, attempt, and preflight digest.
  • Rules for revalidation immediately before execution.
  • One-use and replay-prevention semantics.
  • A minimal binding between execution and outcome evidence.
  • Error behavior and conformance cases for invalid transitions.

What IntentRail would not define

  • Agent identity or credential issuance.
  • A universal authorization token format.
  • A policy language or policy decision service.
  • Reputation, trust scores, or risk scoring.
  • A global evidence store.
  • A replacement for A2A transport bindings or the core task model.

An implementation could use OAuth, capability tokens, signed permits, local policy engines, or another authorization system. IntentRail would define how the result is bound to an A2A task execution, rather than choosing that system itself.

Relationship to existing A2A discussions

DiscussionPrimary concernRelationship to IntentRail
#1769 Verifier-side admission and adjacent permit/evidence/receipt artifacts IntentRail can carry references to those artifacts while defining A2A task and execution invariants
#1716 Capability-token enforcement at the skill boundary A capability token can supply the authorization consumed by IntentRail
#1956 Structured business intent and fulfillment constraints An intent descriptor can supply part of the preflight record
#1976 Requester acceptance or rejection of task output Acceptance can be an outcome signal, but does not prove execution matched authority
#1847 Post-execution receipts linked to upstream authority Such a receipt can supply outcome evidence; IntentRail defines its lifecycle binding

The closest architectural discussion is #1769. It places full verifier artifacts in an adjacent layer and asks A2A to carry references. IntentRail is concerned with the A2A-side lifecycle rules that prevent an authorized request from becoming a materially different or repeated execution.

These approaches can coexist. IntentRail does not require ownership of the permit, policy, or receipt formats referenced by a task.

Initial A2A integration approach

  1. The agent declares support through an AgentExtension URI.
  2. The client activates it using normal A2A extension negotiation.
  3. Records are carried in namespaced task or message metadata, or by stable references where the complete artifact belongs outside A2A.
  4. Existing A2A task states remain unchanged.
  5. The extension defines permitted lifecycle transitions and the checks for each transition.
  6. Unsupported clients and agents continue using ordinary A2A behavior.
The exact metadata shape should be developed through the proposal discussion, not treated as settled in the first issue.

Questions for maintainers and the community

  1. Is an A2A lifecycle profile the right place for this boundary, or should it remain adjacent?
  2. Should the extension define only digest-bound references, or also minimal record shapes?
  3. Should one-use authority be scoped to a task and attempt, or another correlation unit?
  4. Which task transitions best anchor execution revalidation and outcome binding?
  5. Are there other proposals that should be treated as dependencies or prior work?

Request

We are seeking community review and, if maintainers agree that this boundary belongs within A2A's extension model, sponsorship for an experimental-ext-intentrail repository.

Maintainer sponsorship would provide an incubation location and initial oversight. It would not make IntentRail part of A2A core or require existing authorization and receipt proposals to adopt the same architecture.

See the A2A extension and protocol binding governance for the experimental-extension process.

Implementation status

A prototype and conformance work exist, but the implementation repository will remain private while security hardening is completed. This initial proposal is about agreeing on the protocol boundary and incubation direction.
