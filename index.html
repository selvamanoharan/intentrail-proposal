IntentRail: authorization-bound execution for A2A

Status: Discussion draft  ·  Last updated: 21 August 2026  ·  Proposed artifact: experimental-ext-intentrail

IntentRail is a proposed A2A extension for tasks that can cause an external side effect. It makes four things checkable: what was requested, what was authorized, whether that authorization was already used, and what happened after execution.

The proposal is about the execution boundary. It does not change A2A task states or add an identity, policy, payment, or reputation system to A2A.

The problem

Authentication tells a receiver who sent a request. Authorization can say that the sender is allowed to do something. Neither one, on its own, proves that the action executed later is the same action that was approved.

Between approval and execution:

  • parameters can change;
  • a recipient or resource can be substituted;
  • a constraint can expire or be revoked;
  • a retry can become a second execution; or
  • a completion record can describe an unrelated outcome.

Applications can solve this privately with metadata and local state. The interoperability question is whether two A2A implementations can apply the same checks and reach the same result.

Boundary with A2A

A2A continues to define discovery, messages, tasks, task state, and returned artifacts. IntentRail adds a versioned extension binding around an A2A task: 

preflight -> authorization -> execution gate -> outcome -> verification
Compatibility constraint The extension uses existing A2A extension negotiation and namespaced metadata. It does not add values to A2A core enums or reinterpret an A2A taskId.

The four linked records

1. Preflight proposal

The requester records the objective, intended side effect, constraints, requesting party, and creation time. Once submitted, the proposal is immutable. A material change creates a new proposal, optionally linked to the one it replaces.

2. Authorization decision

An authorized party accepts, rejects, or counters the proposal. Acceptance creates an immutable execution contract containing the approved action and constraints. A deployment may attach signed approvals or a signed decision receipt.

IntentRail does not prescribe the policy language, credential, or service used to reach the decision. It requires the execution boundary to verify the decision that it relies on.

3. Execution identity

The accepted contract supplies a stable execution identity, currently called contractId. It is separate from A2A taskId: the contract identifies the authorized lifecycle, while the task identifier keeps its normal A2A meaning.

Immediately before dispatch, the receiver checks the stored contract, caller, constraints, approvals, and state. It reserves the contract atomically and calls the task handler only after that succeeds.

4. Outcome record

After execution, the executor records outcome evidence linked to the contract: what was observed, when it occurred, and which artifacts or digests support it. Evidence is verified, not accepted as true merely because the executor submitted it.

Lifecycle

PROPOSED -> ACCEPTED -> EXECUTING -> COMPLETED -> VERIFIED

PROPOSED -> REJECTED
ACCEPTED -> CANCELLED
EXECUTING -> FAILED
COMPLETED -> COMPENSATION_REQUIRED -> COMPENSATED

An implementation rejects a transition that is not allowed. Successful transitions produce ordered audit records so the current state can be explained later.

Initial A2A carrier

The exact wire shape is open for discussion. A small binding could carry the accepted contract identifier and the material needed to verify execution authorization: 

{
  "version": "draft",
  "contractId": "ctr_123",
  "authorization": {
    "facts": { "environment": "production" },
    "approvals": []
  }
}

The object sits under the extension URI in A2A message metadata. The same URI appears in message.extensions, and the Agent Card advertises support and whether the extension is required.

At the receiving boundary, the implementation:

  1. confirms that the message activated the advertised extension;
  2. loads the contract from a trusted store;
  3. verifies that the authenticated caller may execute it;
  4. checks the contract state, constraints, and approvals;
  5. reserves the execution identity; and
  6. only then calls the A2A task handler.

Retry and replay

Content integrity and replay protection are different concerns. A digest can show that a record changed, but it cannot show whether the action already ran. Replay handling is therefore stateful:

  • an exact transport retry resolves to the existing A2A task or stored result;
  • the same idempotency key with different input is rejected;
  • an accepted contract can enter execution only once;
  • repeated delivery cannot call the task handler again; and
  • crash recovery must not create a second side effect.

Canonicalization is limited to versioned IntentRail records that are hashed or signed. The proposal does not define a universal content identity for every agent action or replace identifiers owned by another protocol.

Initial conformance cases

  1. A valid accepted contract is dispatched once.
  2. Missing or invalid authorization is rejected before dispatch.
  3. A constraint mismatch is rejected before dispatch.
  4. An exact retry returns the existing task without redispatch.
  5. An idempotency key reused with different input is rejected.
  6. A contract already in execution cannot invoke the task handler again.
  7. Outcome evidence linked to another contract is rejected.
  8. An invalid transition leaves stored state unchanged.
  9. A failed outcome can enter compensation without losing its original links.
  10. Crash recovery does not repeat the side effect.
  11. A multi-hop authorization cannot silently widen its approved scope.

Scope

IntentRail would define

  • extension version negotiation and activation;
  • minimum lifecycle records and their linkage;
  • checks required at the execution boundary;
  • retry, replay, and partial-failure behavior;
  • outcome linkage and verification states; and
  • deterministic errors and conformance cases.

IntentRail would not define

  • agent identity or credential issuance;
  • a universal authorization token;
  • a policy language or risk score;
  • a payment or settlement protocol;
  • a global evidence store; or
  • a replacement for A2A transport or task state.

Questions and request

  1. Is this lifecycle narrow enough to be an A2A extension?
  2. Should the binding carry full authorization material, a stable reference, or both?
  3. Which record fields need canonicalization for independent verification?
  4. Which retry, timeout, and crash cases should be mandatory conformance tests?
  5. How should multi-hop authorization be linked without changing A2A task identity?
  6. Which outcome fields belong in metadata, normal artifacts, or external evidence?

If A2A maintainers agree that this boundary belongs in the extension model, I am looking for a maintainer sponsor for an experimental-ext-intentrail repository. I am prepared to maintain the experimental work and its conformance fixtures.

See the A2A extension and protocol binding governance.

Implementation status

A prototype and conformance work exist. The implementation repository remains private while release and security work is completed. This public proposal is intended to be reviewable without access to that code.
